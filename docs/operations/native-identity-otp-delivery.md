# Native identity OTP email delivery operations

**Status:** additive native OTP request, verify, profile/session-context, sign-out, fail-closed native self-deletion that preserves shared workspaces, two-stage email-change, platform-moderation, and support-impersonation routes are implemented under `/v1/identity/*`, but are absent by default. An operator must explicitly set `NIBLEAF_NATIVE_IDENTITY_ENABLED=true` before the routes or native-cookie authorization admission exist. This is a rollout gate, not a production authority cutover: Better Auth remains authoritative until the compatibility and cutover gates in ADR-0008 are complete.

## Additive HTTP contract

The Rust API exposes these additive endpoints; dashboard routing has not been switched from Better Auth:

- `POST /v1/identity/otp/request` accepts only `email` and returns `202`, `Cache-Control: no-store`, and `{ "data": { "challenge_id": UUID } }`. A real sign-in delivery intent returns its opaque challenge ID; malformed and rate-limited input return a fresh UUID of the same shape. The identifier is not a credential—only a stored challenge plus matching one-time code can authenticate—so a browser can continue to verification without turning request responses into an account oracle.
- `POST /v1/identity/otp/verify` accepts that `challenge_id`, `code`, and an optional new-account `name`. It accepts only sign-in challenges, resolves/provisions the user according to `NIBLEAF_DISABLE_SIGNUP`, returns a seven-day native session, and sets the host-only `nibleaf_identity` cookie.
- `GET /v1/identity/session` reads only the native cookie and reports the native session identity plus `{ id, name, email, email_verified }`. It preserves top-level `user_id` for additive-client compatibility. Its `active_organization_id` is the stored active organization only if it remains a live membership; otherwise it deterministically falls back to the first current membership (`createdAt`, then ID), matching the legacy session middleware. This is display/session context, never authorization.
- `POST /v1/identity/csrf` is the narrow native browser recovery route for a still-live `nibleaf_identity` cookie whose one-time in-memory/session-storage CSRF value is absent (for example, a new tab). It requires an explicit exact trusted `Origin`, rotates the session's server-side CSRF-secret hash, and returns the new `{ "csrf_token": string }` once with `Cache-Control: no-store`. It intentionally bypasses the API-wide CSRF header check only for this exact route; all other unsafe native requests still require the rotated token. A recovery invalidates the prior token, including in other tabs.
- `PATCH /v1/identity/profile` accepts only `{ "name": string }`, trims it, rejects blank/control-containing/over-120-scalar names, and updates the current native session user's name. The API-wide native unsafe-request Origin/CSRF admission applies; a target support session therefore has the same target-user behavior as other customer actions, but a revoked, expired, suspended, banned, or no-longer-live-operator support session cannot mutate it.
- `PUT /v1/identity/session/active-organization` accepts only `{ "organization_id": string }` and persists a preference only after proving it is a current membership of the current session user. It has the same API-wide native Origin/CSRF admission. It does not grant tenant or object authorization; every feature must continue to authorize from its own live object/membership scope.
- `POST /v1/identity/sign-out` requires exact trusted Origin admission, the native cookie, and the `X-CSRF-Token` returned by verify. It revokes the session and clears that host-only cookie.
- `POST /v1/identity/account-deletion` is intentionally a narrow destructive subset, not tenant-erasure parity. It requires a direct, live native session plus the API-wide exact-Origin/CSRF fence. The transaction locks and revalidates the exact session/user, rejects impersonation, locks provisioning events, and rejects an already `processing` worker-owned intent. It can delete a zero-membership account and can also preserve a shared workspace: memberships, organizations, and their members are locked; if the departing account is the sole owner, the earliest other member becomes owner before the departing membership is removed. A **sole-member** workspace returns `409` with no mutation because it needs retained-store erasure. On success pending `identity.account.provision_requested` events become `dead_letter`, immutable opaque deletion evidence is appended, and the user is deleted atomically. The native cookie is cleared only after commit and the response is `204` with `Cache-Control: no-store`. A conflict deliberately leaves the session/cookie intact; do not bypass it with relational SQL. Sole-tenant deletion remains unavailable until retained-store erasure is implemented and tested.
- `POST /v1/identity/email-change/request` requires a native-cookie-authenticated actor and starts a two-stage current-mailbox proof. With a configured delivery provider it returns a generic `202` plus `{ "data": { "challenge_id": UUID } }` for accepted, malformed, taken, unchanged, and rate-limited targets. For every non-rate-limited request by a live user it deliberately issues the current-mailbox OTP—even when the requested target is malformed, unchanged, or taken—so arrival of that email cannot enumerate target ownership. Only an eligible target gets a durable email-change state record; decoy handles cannot produce a new-mailbox OTP. Rate-limited/unavailable outcomes receive a fresh random UUID of the same shape. The handle is opaque but not secret: the same native user and its OTP proof are still required.
- `POST /v1/identity/email-change/verify-current` accepts that current-stage `challenge_id` plus the current-mailbox code and requires the native cookie plus the API-wide unsafe-request Origin/CSRF fence. A real flow atomically consumes only that account's `verify_email` proof, queues a separate `change_email` proof for the requested new mailbox, and returns its next opaque challenge ID. A fake, stale, foreign, wrong-code, expired, target-raced, or malformed continuation still receives a fresh UUID-shaped `202`; only a real flow sends the next email. This makes the browser contract usable without weakening target-email anti-enumeration.
- `POST /v1/identity/email-change/confirm` accepts the returned new-mailbox `challenge_id` plus code and requires the same native admission fence. It consumes only the associated new-mailbox challenge, confirms that the old address has not changed, updates the existing user email, and returns `200`; stale, foreign, wrong-purpose, expired, consumed, or invalid final proofs are rejected.
- `POST /v1/identity/admin/users/{user_id}/suspend` and `/unsuspend` require the native cookie plus API-wide unsafe-request admission and a live platform `user.role='admin'`. Suspension atomically sets legacy-compatible moderation fields, revokes all native sessions, deletes bridge sessions, and returns `{ "data": { "changed": boolean } }`; unsuspension does not resurrect a session. A platform administrator cannot be suspended.
- `POST /v1/identity/admin/projects/{project_id}/takedown` accepts only `{ "reason": string | null }` (optional; trimmed, control-character-free, at most 500 Unicode scalar values) and applies the same native platform-admin fence. `/restore` clears the existing takedown fields. Both return the same `changed` response. New publications are already refused by the project publishing slice while `takedownAt` is present.
- `POST /v1/identity/admin/impersonations` accepts `target_user_id` and optional `active_organization_id`. A direct live native platform administrator receives a separate one-hour target session; the response returns its `impersonation_id`, target `user_id`, expiry, and target-session CSRF secret once. It replaces `nibleaf_identity` with that target session and sets a path-scoped operator-resume cookie; no raw token appears in JSON.
- `POST /v1/identity/admin/impersonations/stop` requires an explicit trusted `Origin` and the path-scoped `nibleaf_identity_resume` cookie. It ends a live support session when present, clears the resume cookie, and restores the original operator native cookie. This narrow endpoint remains callable after target-session expiry or emergency revocation so the operator is never stranded. It does not accept a Better Auth bridge credential.
- `POST /v1/identity/admin/impersonations/{impersonation_id}/revoke` is the direct-native-platform-admin emergency revocation path. It revokes the target session and appends a `revoked` audit fact; repeating it after termination returns `changed:false` without rewriting history.

OTP request/verification, native self-profile/session, email-change-continuation, and sign-out responses use `Cache-Control: no-store`. The verify response intentionally returns the CSRF secret exactly once; it is not stored in an accessible cookie and browsers must retain it only in their authenticated in-memory/client session mechanism. Cookie authentication remains `HttpOnly`, host-only, `SameSite=Lax`, and `Secure` when `NIBLEAF_APP_URL` is HTTPS.

API-wide native admission now injects a native `Actor` into the existing Rust feature extractors. A request bearing `nibleaf_identity` therefore cannot also carry a legacy bearer credential or `nibleaf_session` cookie. Unsafe feature routes using a native cookie require exact trusted Origin and `X-CSRF-Token` before their own authorization handler runs, except the exact `POST /v1/identity/csrf` recovery route, which requires explicit exact Origin and rotates/returns the token itself. This is additive: legacy Better Auth requests retain their current transition extractor semantics.

## Native moderation operations

Migration `202610150007_identity_moderation_audit.sql` adds the append-only `rust_identity_moderation_audit` table and a database trigger that rejects ordinary row update/delete operations. A native moderation command re-reads the caller's active platform-admin role **inside the same PostgreSQL transaction** as the moderation mutation and audit insert. The audit row retains opaque actor/target identifiers rather than cascading foreign keys, so future account/project deletion cannot erase an operator fact. It records the native actor's current session identifier, constrained action, exactly one user/project target, optional safe reason, whether the action changed state, and time.

Suspension is atomic across the legacy-compatible user moderation fields, every open `rust_identity_session`, every Better Auth bridge `session`, and the audit fact. Before its broad target-session revocation, it locks every active native support lifecycle whose target is the suspended account and terminalizes it with a moderator-attributed `revoked` support audit fact in the **same transaction**. This prevents a suspended target from leaving an active-looking support lifecycle even though its cookie would already fail authentication. The bridge-session deletion is deliberate during the bounded migration: a native moderation action must not leave an alternate transition credential usable. Repeated suspend/unsuspend/takedown/restore requests do not fail merely because state already matches; they return `changed:false` and still produce an audit fact. No native moderation list/query endpoint or dashboard view exists yet; operators use the existing administration surface until its separately reviewed migration.

## Native support impersonation operations

Migration `202610150008_identity_impersonation.sql` adds a mutable `rust_identity_impersonation` lifecycle fence and immutable `rust_identity_impersonation_audit` facts. A start transaction locks the live operator and target rows in deterministic order, verifies the operator's direct platform role and current non-impersonated native session, verifies the target is not banned/suspended, optionally validates the target's organization membership, issues a distinct one-hour target session, and writes both lifecycle and `started` audit rows atomically. One operator session can have at most one active support context.

The target session has `impersonated_by` set to the operator user ID. `GET /v1/identity/session` returns that marker so a later native client can display an unambiguous support-access banner. Target feature authorization continues to run as the target; platform administration rejects every actor carrying this marker, even if the target happens to hold an admin role. Native authentication also rejects an impersonated session if its originating operator is no longer an active platform admin.

The only browser preservation of the operator credential is `nibleaf_identity_resume`: host-only, `HttpOnly`, `SameSite=Lax`, Secure under HTTPS, and scoped to the exact stop route. It is not read by normal native admission and is not sent to customer feature routes. The stop route has a deliberate special admission path because revocation/expiry may invalidate the active target cookie before the browser can exit. It requires an **explicit** exact trusted `Origin` (originless requests are rejected), authenticates the resume session server-side, writes an `ended` fact if a live support context remains, restores the regular operator cookie, and clears the scoped resume cookie. If another administrator already revoked the context, it still restores the valid operator session but returns `changed:false` rather than fabricating an end event.

Emergency revocation updates the lifecycle record, revokes the target native session, and writes a `revoked` fact in one transaction. Native suspension of a support target uses the same lifecycle terminalization inside the moderation transaction, with the suspending moderator's user/session attribution, before revoking all of that target's sessions. If the target support session instead uses generic native sign-out, sign-out terminalizes the matching support lifecycle and writes `ended` atomically before clearing the target cookie. An expired support context is denied by the normal session expiry check. If encountered later by a new start, stop, or emergency revoke, the workflow terminalizes it and appends an `expired` fact.

The worker also runs a cancellation-aware periodic reconciler. Each pass locks at most 100 lifecycle rows due at database `NOW()` in `(expires_at, id)` order using `FOR UPDATE SKIP LOCKED`, conditionally fences each row with `terminated_at IS NULL`, revokes the target native session, and appends the immutable fact in the same transaction. Multiple workers therefore make bounded non-blocking progress; a crash rolls back the selected batch and a later pass retries it. This is an idempotently fenced, at-least-once scheduler—not an exactly-once claim. New expiry facts carry `actor_kind='system'`, `actor_user_id='system:identity-impersonation-expirer'`, and a null actor session; human `started`, `ended`, and `revoked` facts retain a user actor and exact session. Migration `202610150009_identity_impersonation_expiry_reconciler.sql` preserves any older user-attributed expiry evidence while adding those system-actor constraints and the active-expiry index. Existing dashboard/Better Auth support access remains authoritative until its native request/cookie/banner/redirect compatibility work is migrated.

## Native account deletion that preserves shared workspaces

Migration `202610150010_identity_account_deletion_audit.sql` creates `rust_identity_account_deletion_audit`; `202610150011_identity_account_deletion_shared_memberships.sql` adds the shared-workspace departure action. The table stores only an opaque deleted user ID, exact native session UUID, constrained action, and time; it has no foreign key to the account so relational deletion cannot erase the fact. A trigger rejects ordinary updates and deletes. Treat this as security/operational evidence: do not truncate it as an application rollback shortcut.

This implementation protects the provisioning race without pretending to erase a tenant. It locks the current user, all departing memberships/organizations, and each organization’s member rows before deciding whether departure is safe. If another member exists, the tenant stays intact; when the departing account is the only owner, it is demoted and the earliest other member is promoted before the departing membership is removed. The organization lock prevents a concurrent member insert from changing the sole/shared decision. A sole-member organization returns `409` with no mutation because retained-store erasure is still required.

An in-flight provisioner that already read the user can still reach its member insert, but its foreign-key lock waits. If it committed first, deletion observes the membership and preserves/transfers the shared workspace; if deletion wins, the user disappears and the provisioner's member insert fails, rolling back its workspace transaction. A currently leased provisioning event receives `409`; inspect normal worker health and let it finish rather than forcing its state. A merely pending event is terminally cancelled with the fixed reason `identity account deleted before workspace provisioning`.

Do **not** use this endpoint to delete a sole-member workspace. Legacy behavior may invoke retained-store erasure. Before expanding it to that case, implement and exercise a durable workflow that explicitly covers pending usage receipt fencing, ClickHouse analytics/usage deletion, durable search deletion, object storage/assets, exports, Git-related records, and every other retained external system. It must be safe to retry and must not report relational completion as full erasure. The selected policy for the next native tenant-erasure slice is fail-closed: if a tenant has a Git connection or externally managed custom domain, the workflow must stop before deleting data or relational state until a separately reviewed provider-side retention/disconnect policy exists.

## Email-change lifecycle

Migration `202610150006_identity_email_change.sql` adds the identity-owned `rust_identity_email_change` state machine. A row moves only from `pending_current` to `pending_new` to `completed`; a replacement request explicitly cancels a previous active row. Database constraints require normalized distinct old/new email values, bind distinct current/new challenge IDs, and permit only one active change for a user.

The request transaction locks the user, rejects an unchanged or already-owned target without leaking which case occurred, cancels any active flow, creates a `verify_email` OTP for the current normalized address, encrypts its delivery payload, and appends its outbox intent. Current-proof verification consumes that exact OTP and, in the same transaction, checks that the target remains free, creates/enqueues a `change_email` OTP for the target, and advances the row. Confirmation consumes the target OTP and conditionally updates `user.email` only when its current normalized value still matches the recorded old address; it also sets `emailVerified=true` and records completion. OTP code hashes remain one-way; only a short-lived delivery payload is encrypted for the worker.

The HTTP continuation deliberately carries only the opaque OTP challenge identifier: request returns the current-proof handle and current verification returns the new-proof handle. Request and current verification return a UUID-shaped `202` even for ordinary rejected states, and their continuation responses are `Cache-Control: no-store`; the client must proceed to the next code form without learning whether a target was taken. Only a valid final new-mailbox code can distinguish success by changing the authenticated session profile.

All three HTTP endpoints require native identity rollout and a valid `nibleaf_identity` cookie even when another legacy credential could otherwise identify an actor. Because they mutate state, API-wide native admission enforces exact trusted `Origin` and `X-CSRF-Token` before the handler. The request and current-proof endpoints also refuse with `503` if neither Postmark nor SMTP is configured: the service must not acknowledge an operation whose required email proof cannot be delivered. The dashboard remains on Better Auth until its native request/cookie/state compatibility work is complete.

## Delivery contract

`queue_otp_challenge_delivery` commits all of the following in one PostgreSQL transaction:

1. rotates any pending OTP for the normalized email and purpose;
2. persists only a one-way OTP hash in `rust_identity_otp_challenge`;
3. stores the raw six-digit OTP only as an authenticated encrypted short-lived payload in `rust_identity_otp_delivery`;
4. appends the platform-scoped `identity.otp.delivery.requested` event to `outbox_event`.

The outbox payload has only `delivery_id`; it never contains the code, email address, or ciphertext. Authentication begins before a user is necessarily a member of an organization, so this narrowly scoped event has a null `tenant_id`. Tenant-owned events continue to require a tenant ID and organization foreign key.

The worker claims the event using the normal outbox lease, loads the delivery row, verifies the challenge has not expired or become terminal, decrypts the payload, renders the purpose-specific message, and calls Postmark or SMTP without holding a database transaction. It records the provider name and receipt, clears ciphertext to zero bytes, and marks the delivery delivered. Acknowledgement loss remains **at-least-once**: a crash after a provider accepts an email can lead to a resend. The design does not claim exactly-once email delivery.

Expired, consumed, locked, or rotated challenges are cancelled without sending, and their ciphertext is cleared. A delivery event that is reclaimed after its delivery row is already delivered/cancelled is idempotently acknowledged without a second provider call.

## Required configuration

`NIBLEAF_IDENTITY_DELIVERY_ENCRYPTION_KEY` is required by both Rust binaries. It must be a base64-encoded **32-byte key** and must be distinct from `NIBLEAF_INVITATION_SIGNING_KEY`.

`NIBLEAF_TRUSTED_ORIGINS` is a comma-separated exact origin allowlist for future unsafe native identity routes. When omitted, it defaults to `NIBLEAF_APP_URL`; it must be set explicitly before a multi-origin deployment. `NIBLEAF_DISABLE_SIGNUP` (or legacy `DISABLE_SIGNUP`) accepts only `true` or `false` and controls native account creation. `NIBLEAF_NATIVE_IDENTITY_ENABLED` also accepts only `true` or `false` and defaults to `false`; it must remain false until the environment has validated provider delivery, trusted origins, monitoring, rollback, and the ADR-0008 release gates.

`NIBLEAF_SUPPORT_EXPIRY_RECONCILIATION_INTERVAL_SECONDS` configures the worker's support-session expiry cadence. It defaults to `30`; startup rejects provided values that are malformed or outside the inclusive `5`–`300` second bound. Keep it short enough for audit freshness but do not reduce it below the enforced minimum to compensate for a backlog: each pass is capped at 100 rows, exports success/error/duration/item metrics, and the next pass continues the backlog. The worker startup schema check requires the `202610150009` system-actor audit constraint, so an older migration chain fails before it can run an incompatible reconciler.

Identity-delivery encryption now uses a bounded versioned key ring. `NIBLEAF_IDENTITY_DELIVERY_ENCRYPTION_KEY_VERSION` is the positive decimal version written into new ciphertexts and defaults to `1` for compatibility. `NIBLEAF_IDENTITY_DELIVERY_PREVIOUS_KEYS` is optional and may contain **at most two** comma-separated `version:base64-32-byte-key` entries. Versions and key materials must be distinct from the current key and each other; invalid, duplicate, zero, or over-capacity entries stop either Rust binary at startup. The API encrypts only with the current key; the worker constructs the current-plus-retained ring to decrypt pending OTP deliveries.

For rotation, choose a new unused version and deploy **both** API and worker with the new current key/version plus the old current key in `NIBLEAF_IDENTITY_DELIVERY_PREVIOUS_KEYS`. Do not change the current key in place at the same version. Keep the previous key through the OTP TTL plus the maximum outbox delivery-retry horizon, and until no pending/processing delivery ciphertext begins with its two-byte big-endian version. Only then deploy again without that retained entry. This preserves decryptability during a rolling deploy without retaining an unbounded historical key set.

Email provider selection is the established Postmark-first/SMTP-fallback configuration:

- `NIBLEAF_EMAIL_FROM` / legacy `EMAIL_FROM`;
- `NIBLEAF_POSTMARK_API_KEY` / legacy `POSTMARK_API_KEY`;
- optional `NIBLEAF_POSTMARK_MESSAGE_STREAM` / legacy equivalent;
- `NIBLEAF_SMTP_URL` / legacy `SMTP_URL` fallback.

An absent provider is an operational configuration error. The native OTP and email-change request/proof routes refuse to acknowledge a delivery-dependent operation when neither provider is configured; existing already-queued events classify the absence as retryable until their retry budget is exhausted. Monitor pending and dead-letter outbox metrics; do not make OTP routes public until an environment has an email provider configured and delivery E2E coverage is enabled.

## Account and workspace provisioning

A successful native sign-in OTP for an unknown canonical email may create a `user` row only when `NIBLEAF_DISABLE_SIGNUP=false`. The same transaction appends `identity.account.provision_requested`; it never creates a Better Auth `session` or `account` row. Existing membership and either a live legacy invitation or native member invitation suppress unrelated workspace creation.

This is intentionally asynchronous, matching the legacy hook's non-blocking shape. The worker now creates an owner workspace plus a `Documentation` project (`docs`, with collision-safe suffixes), default `en`/`main`, onboarding record, and the seven-page rich starter tree that was ported from the current Better Auth source: Getting started, Installation, Components tour, API reference with Authentication/Create a widget children, and FAQ. All rows plus `project.initialized` and tenant-scoped `starter.publication.requested` outbox intents commit together.

The publishing feature consumes that starter intent under the normal project advisory lock. It creates exactly one `PENDING` v1 deployment with commit message `Publish starter site`, atomically emits the ordinary `publication.requested` intent, and the existing worker transitions it to `READY`. Re-delivery and a user publication that wins the race are no-ops rather than a second first deployment. This is durable at-least-once internal work; it does **not** claim exactly-once publication.

The legacy initialization still writes Harbor theme metadata, default project-add-on/audit rows, and a best-effort analytics platform event that Rust does not currently create. Those are documented parity differences; the starter content and automatic first-publication release blocker is no longer open. The dashboard remains on Better Auth until all browser and cutover gates pass.

## Migration and rollback

Apply `202610150005_identity_otp_delivery_outbox.sql`, `202610150006_identity_email_change.sql`, `202610150007_identity_moderation_audit.sql`, `202610150008_identity_impersonation.sql`, `202610150009_identity_impersonation_expiry_reconciler.sql`, `202610150010_identity_account_deletion_audit.sql`, and then `202610150011_identity_account_deletion_shared_memberships.sql` after the existing Rust migrations. They are additive except for allowing `outbox_event.tenant_id` to be null for platform-scoped events; they do not alter existing tenant event data or remove Better Auth tables. Migration `202610150009` is transactional: it retains historical user-attributed expiry rows, adds constrained `actor_kind` support for the named sessionless system actor, and creates the stable-predicate active-expiry index. Migration `202610150010` creates immutable account-deletion evidence without user foreign keys; `202610150011` expands its constrained action set for safe shared-workspace departures. The API verifies that expanded constraint at startup, so a database stopped at `202610150010` fails before serving traffic rather than failing a valid shared-workspace departure at request time. Never roll back or truncate the native moderation, impersonation, or account-deletion audit tables as part of an application rollback; all are security evidence.

Before rolling back a binary that cannot process `identity.otp.delivery.requested` or `starter.publication.requested`, drain or explicitly dead-letter those events after a security review. Do not delete a delivery row merely to make an outbox alert disappear; its receipt and state are incident evidence.
